# 작업 전후 비교

속도와 토큰을 줄이는 작업(가지치기, 조기 종료)의 효과를 같은 질문의 작업 전·후 실행으로 비교한다. 정답과 대조하는 채점은 하지 않는다. 비교하는 것은 두 가지다.

| 비교 | 보는 것 | 답하는 물음 |
|---|---|---|
| **1. 응답 변화량** | 같은 질문에 대한 작업 전 응답과 작업 후 응답이 얼마나 달라졌나 | 줄인 뒤에도 답이 비슷한가 |
| **2. 보고서 선택 변화** | 작업 전과 후에 읽은 커뮤니티 보고서와 응답이 인용한 보고서가 어떻게 달라졌나 | 버린 보고서가 작업 전 답에 쓰이던 것인가 |

속도와 토큰은 줄이려는 값이라 따로 채점하지 않고 실행 기록에서 읽는다([4절](#4-속도와-토큰)).

이 비교가 보여 주는 것은 작업 전과 얼마나 같은가이지, 정답과 얼마나 맞는가가 아니다. 작업 전 응답이 틀렸다면 변화가 없어도 틀린 채로 유지된 것이다.

## 1. 작업 전 기준

작업 전은 2층까지 보고서 4,036개를 모두 읽는 graphrag global 검색이다. 작업 후 실행은 같은 질문 문서, 같은 프롬프트 방식, 같은 층(2층), 같은 모델로 돌린다. 조건이 다르면 그 영향이 응답 변화량에 섞인다.

작업 전 기록은 `results/20261127-211144_L2_before` 한 폴더에 45문항이 모두 있다. 문항마다 프롬프트 방식이 다르다.

| 문항 | 프롬프트 | 기록을 만든 실행 |
|---|---|---|
| Q01, Q03~Q09, Q11~Q30 (28문항) | 공통 지시문 + 유형별 지시문 + 질문 | 2026-11-27에 새로 실행 |
| Q02, Q10 | 공통 지시문 + 유형별 지시문 + 질문 | `results/20261125-233422_L2_Q02Q10`에서 복사 |
| Q31 | 질문만 (`--plain`) | `results/20261126-001259_L2_Q31_plain`에서 복사 |
| Q32~Q45 | 질문만 (`--plain`) | `results/20261125-233422_L2_broad_plain`에서 복사 |

- 출처는 `run.json`의 `sources`에 적혀 있다. 복사한 기록은 원본과 바이트까지 같고, 프롬프트가 현재 질문 문서로 만든 것과 같은지 확인했다.
- `results/20261124-131354_L2`는 옛 지시문(끝에 '확인 불가' 문장)으로 돌려서 쓰지 않는다. 그 문장을 빼면 달라지는 문항이 있다. Q05와 Q08은 옛 기록에서는 응답이 있었지만 새 기록에서는 답 없음(정형 문장)이다.
- `--plain`은 실행 단위로만 켜진다. 작업 후에도 Q01~Q30과 Q31~Q45를 따로 돌려야 한다.
- 작업 후 실행도 `records/Q??.json`에 같은 항목(`question`, `response`, `status`, `cited`, `batches[].report_ids`, `context`, `seconds`, `usage_estimate`)을 남기게 만든다. 아래 비교가 모두 이 항목에서 나온다.

## 2. 응답 변화량

문항마다 작업 전 응답과 작업 후 응답(기록의 `response`)을 LLM에게 보여 주고 얼마나 달라졌는지 판정하게 한다. 계산식은 쓰지 않는다. 문자열 비교는 표현만 바뀌어도 크게 달라진 것으로 나와서, 내용이 바뀌었는지 알려 주지 못한다.

| 값 | 얻는 방법 |
|---|---|
| **변화** | LLM 판정 한 가지. `같음`(담은 사실이 같다), `조금 다름`(핵심은 같고 일부 사실이 빠지거나 새로 생겼다), `많이 다름`(결론이나 주요 사실이 다르다) 중 하나 |
| **빠진 내용, 새 내용** | 같은 판정에서 LLM이 한 줄씩 적는다. 작업 전에만 있던 사실과 작업 후에만 생긴 사실이다 |
| **상태** | `status`가 바뀌었는지 (`answered` ↔ `no_data`). 기록에서 바로 읽는다 |
| **글자 수** | 작업 전 → 작업 후 (`summary.csv`의 `response_chars`) |

판정은 문항당 LLM 호출 1회다. 질문, 작업 전 응답, 작업 후 응답을 보내고, 응답 속 `[Data: …]` 인용 표시는 뺀다(보고서 선택은 3절에서 따로 본다). 모델은 `gpt-6-luna`, 프롬프트는 아래 것으로 고정하고 결과 표와 함께 적는다.

```text
다음은 같은 질문에 대한 두 응답이다. 응답 A는 작업 전, 응답 B는 작업 후다.
질문이 요구한 내용(값, 항목, 결론)을 기준으로 B가 A와 얼마나 달라졌는지 판정하라.
표현이나 순서가 달라도 담은 사실이 같으면 달라진 것이 아니다.

변화: 같음, 조금 다름, 많이 다름 중 하나
- 같음: 담은 사실이 같다.
- 조금 다름: 핵심 내용은 같고 일부 사실이 빠지거나 새로 생겼다.
- 많이 다름: 결론이나 주요 사실이 다르다. 한쪽만 답하지 못했다고 한 경우도 여기에 든다.
빠진 내용: A에는 있고 B에는 없는 사실. 한 줄씩. 없으면 "없음"
새 내용: B에는 있고 A에는 없는 사실. 한 줄씩. 없으면 "없음"

[질문]
(질문)

[응답 A]
(작업 전 응답)

[응답 B]
(작업 후 응답)
```

- LLM 판정도 같은 쌍에서 달라질 수 있다. `많이 다름`으로 나온 문항은 사람이 두 응답을 읽어 확인한다.
- 같은 조건으로 두 번 돌려도 응답은 다르게 나온다. 작업 후 판정이 이 자연 변동보다 큰지 보려면, 작업 후를 돌리는 날 몇 문항을 작업 전 방식으로 한 번 더 돌려 작업 전끼리도 같은 방식으로 판정해 둔다(4절의 같은 날 속도 기준과 겸한다).

## 3. 보고서 선택 변화

기록의 두 값으로 비교한다. 번호는 모두 보고서의 `community` 번호다.

- **읽은 보고서**: `batches[].report_ids`를 모은 집합. map 단계에 보낸 보고서다. 작업 전은 2층 전체(4,036개)다.
- **인용한 보고서**: 응답의 `[Data: Reports (…)]`에 적힌 번호(`cited.by_kind.Reports`). 응답이 근거로 든 보고서이며, 읽은 보고서의 일부다.

| 값 | 뜻 |
|---|---|
| **읽은 수** | 작업 전 → 작업 후, 줄어든 비율 |
| **읽기 유지** | 작업 전 응답이 인용한 보고서 중 작업 후에도 읽은 비율. 낮으면 쓰이던 보고서를 버린 것이다 |
| **인용 유지** | 작업 전 응답이 인용한 보고서 중 작업 후 응답도 인용한 비율 |
| **새 인용** | 작업 후 응답만 인용한 보고서 수 |

- 작업 전 응답이 인용한 보고서가 없으면 읽기 유지와 인용 유지는 계산하지 않는다.
- 인용 목록이 `+more`로 잘린 응답(`cited.has_more`가 참)은 인용 유지가 실제보다 낮게 나올 수 있어 표시한다.

## 4. 속도와 토큰

| 값 | 읽는 곳 |
|---|---|
| **속도** | 기록의 `seconds`(질문 하나가 끝나기까지 걸린 시간). 한 문항의 차이보다 문항 평균으로 본다 |
| **map 호출 수** | 기록의 `context.n_batches` |
| **토큰** | 문항별은 기록의 `usage_estimate`, 전체 합계는 `enron/logs/query.log`의 실행별 Metrics 합계 |

- 기록의 `usage_estimate`는 실제보다 낮다. 질문 문장(map 호출마다 붙는다)과 reduce가 빠지고 출력 토큰도 낮게 잡힌다. 작업 전 30문항은 입력과 출력을 합해 약 3%, 출력만 보면 186만 대 327만(기록 대 `query.log`)이었다.
- `query.log`에도 최종 reduce(스트리밍) 호출의 토큰은 잡히지 않는다. 작업 전 30문항에서 27회였다.
- `query.log`는 실행 단위 합계만 남기고 저장소에도 올라가지 않는다. 작업 전 합계는 새로 돌린 28문항(Q01, Q03~Q09, Q11~Q30)만 `run.json`의 `query_log_metrics`에 옮겨 두었다. 합계를 비교할 때는 작업 후에도 같은 28문항을 한 실행으로 돌린다. 나머지 17문항은 기록의 `usage_estimate`로 비교한다.
- 작업 전 기록의 시간은 실행일이 섞여 있다(28문항은 11월 27일, 17문항은 11월 25~26일). 속도는 API 상황에 따라 날마다 달라질 수 있으니, 작업 후를 돌리는 날 몇 문항을 작업 전 방식으로 한 번 더 돌려 같은 날 기준을 만든다. 실행 중에 컴퓨터가 절전에 들어가면 그 문항의 시간이 어긋나므로(작업 전 기록을 만들 때 Q03이 그랬다) 절전을 끄고 돌린다. macOS는 명령 앞에 `caffeinate -i`를 붙인다.
- 달러는 쓰지 않는다. 프롬프트 캐시 때문에 실행 순서와 간격에 따라 달라진다.

## 5. 결과 정리

문항마다 한 줄로 적는다. 한 줄에는 문항, 응답 변화(판정), 상태, 읽은 수(전 → 후), 읽기 유지, 인용 유지, 새 인용, map 호출·토큰·시간(전 → 후)이 들어가고, `많이 다름`인 문항에는 빠진 내용과 새 내용을 붙인다. 마지막에는 판정별 문항 수(같음, 조금 다름, 많이 다름)와 나머지 값의 평균을 적는다.

두 기록 폴더에서 이 값을 뽑고 판정을 호출하는 스크립트는 아직 없다.

## 이전 방법

정답표와 채점 방법 A·B·C(정답 채점, 기준 사실 채점, reduce 입력 점검)는 너무 복잡해서 쓰지 않기로 하고 2026-11-27에 문서를 지웠다. 이전 문서는 git 기록에 있다. 예: `git show 747dd8e:docs/scoring_abc.md`, `git show 747dd8e:docs/questions_b_2001_evidence.md`
